# Shared type definitions audit

Date: 2026-09-21

## Scope and method

This audit covered TypeScript declarations, inline object types, Drizzle schema types, provider
transport shapes, API response types, component props, scripts, tests, and the standalone Railway
worker. The review traced each candidate to its producer and consumers rather than grouping types
only because their fields looked similar. The product specifications make that distinction
important: persistence rows, normalized domain objects, provider payloads, and public API views
have different authorities and should not be collapsed into one universal model.

The installed Next.js 16.3.5 documentation was also checked before changing route types. It
documents the generated `PageProps` and `RouteContext` helpers used in this pass.

## Critical assessment

The codebase already has useful boundaries:

- `src/domain/types.ts` owns catalog, order, quote, holding, and record read models.
- `src/providers/contracts.ts` owns provider capabilities, while upstream JSON shapes remain local
  to the adapter that validates or interprets them.
- `src/db/schema.ts` owns persistence. Drizzle table definitions are not treated as substitutes for
  application or HTTP types.
- Small component-only view state, such as basket form selection and market-lane tabs, stays local.

The main weakness was not a shortage of types; it was repeated definitions at real boundaries.
Several repetitions could drift independently:

1. Order-leg and order aggregate state values were declared separately in the domain model and
   Drizzle schema. A new state could therefore compile in one layer while being rejected by the
   database.
2. Jupiter exact-input request fields were copied four times across the provider interface and its
   implementation.
3. Auth challenge and fresh-authorization shapes were copied in runtime state and serialized state.
4. The `{ state, listings }` market feed was repeated in two screens while the API producer had no
   declared return contract.
5. Recognition results and created-share responses had a server-owned shape and a separate,
   weaker client-only copy.
6. Login, account, wallet, and wallet-signing responses were redeclared at client call sites. The
   signing response in particular is security-sensitive and benefits from literal `false`/`true`
   fields remaining exact.
7. App page and route handler parameter shapes manually repeated types generated by the installed
   Next.js version.

There is no evidence that a single global `types.ts` barrel would improve this repository. It would
couple browser UI, provider internals, persistence, and financial domain code and would make it
easier to accidentally expose server-only fields. Shared definitions should remain owned by the
narrowest stable domain or boundary.

## Implemented high-confidence changes

- `legStates`, `orderStates`, and `userRoles` now provide the domain and Drizzle enum values from
  one source. Existing values and migration SQL are unchanged.
- Internal `LegState`, `OrderState`, `OrderType`, and inventory-scope aliases remain private to the
  module because no external consumer needs to import them.
- `ExactInputQuoteRequest` is the single Jupiter quote request contract used by `QuoteProvider` and
  all `JupiterBuildProvider` methods. Its response helper is private because consumers use the
  provider interface rather than importing that alias directly.
- `AuthChallenge` and `FreshAuthorization` are shared by the in-memory store and state serializer.
- `MarketFeed<Listing>` is shared by both market screens and explicitly annotates both API
  producers.
- `RecognitionMatch` is shared by recognition production, scan state, and scan-result restoration.
  The former free-form `state` and `confidenceBand` strings are now exact unions.
- `CreatedShare` is the shared result of share creation and its client consumer.
- Focused identity boundary types now cover login challenges, account summaries, wallet summaries,
  signing challenges, signing proofs, and signing verification. The server uses `satisfies` so an
  accidental response drift is caught without hiding additional authorized fields.
- The catch-all page and API route now use Next.js-generated `PageProps` and `RouteContext` types.
- Export modifiers were removed from implementation-only aliases and constants so they are not
  presented as a public type API.

## Deliberate non-consolidations

- Drizzle rows were not aliased to domain or API models. Database columns include encrypted,
  historical, and operational fields with different nullability and exposure rules.
- `PreStocksRow` in the standalone Railway worker was not merged with `PreStocksListing`. The
  former is a minimal independently deployed ingestion payload; the latter is the normalized web
  adapter output. Making the worker import the application adapter would increase deployment
  coupling and still would not provide runtime validation.
- Raw Jupiter, Helius, Magic, OpenRouter, PreStocks, and xStocks response structures remain local to
  their adapters. They are external transport details, not Shelf domain contracts.
- Component props and form-only state remain colocated when they have one consumer. Sharing these
  would add indirection rather than prevent drift.
- `PageAccess` was not merged with `UserRole`: public/member/owner page policy and member/owner
  persisted roles represent different sets.
- `SponsorSigner` remains exported even though activation is gated. It is an explicit required
  provider boundary in the approved architecture, not a generic helper or duplicate type.

## Recommendations not implemented

1. Introduce endpoint-specific Zod schemas incrementally when the API controller is split into
   domain routers. A shared TypeScript alias does not validate network JSON, and adding a large
   static API map now would create false confidence around the generic `apiRequest<T>` cast.
2. Infer upstream provider response types from their existing Zod schemas where doing so does not
   expose a raw provider payload as a domain type. This is worthwhile as each adapter is next
   modified, but a broad mechanical rewrite would overlap runtime-validation work.
3. Replace the generic `Record<string, unknown>` store collections with named, validated domain
   records. That is a strong-types task rather than type consolidation: the shapes must first be
   researched from every mutation and persistence path.
4. Keep checking exports with Knip. A type may be necessary inside an exported interface without
   itself needing to be exported.

## Verification

- `npm run typecheck` — passed.
- `npm run lint` — passed with no warnings.
- `npm test` — 8 files and 23 tests passed.

No database migration or serialized-state transformation is required: all implemented changes are
compile-time ownership improvements, and persisted enum values and object fields are unchanged.
